## 3. Hidden-Scope Callouts

### L3 — "and any other place where loading operations happen"

As written, this is open-ended across the entire app. Every Server Component page with `force-dynamic` has this characteristic — navigating to any page shows no loading indicator until the server round-trip finishes. Implementing it truly "everywhere" would mean adding `loading.tsx` files for every route segment plus transition states in every client component that calls `router.push`. That's 10–15 files and 2–3 days of work.

**Constrained interpretation (recommended):** Add a `useTransition`-based loading state to `ListPageControls` so the My/All toggle and company filter show visual feedback during navigation (a spinner or opacity change while the transition is pending). Add `loading.tsx` stubs for the `/inquiries` and `/projects` route segments so their full-page navigations also feel responsive. No broader streaming overhaul. This is 2–3 hours of work instead of days.

The human must confirm the constraint before the batch starts.

### C5 — Live currency formatting (INR/AED vs USD grouping)

The INR grouping is 2-2-3 from the right (e.g. `12,34,56,789`), not Western 3-3-3. Implementing this correctly as-you-type requires:
- A controlled `<input>` that reformats the raw value on every `onChange`
- Caret/cursor position correction after reformatting (otherwise the cursor jumps to the end on every keystroke — a UX-breaking regression)
- Handling of paste (paste raw digits, reformat), backspace-through-commas (delete the digit behind the comma, not just the comma), and programmatic value setting

This is approximately 80–150 lines of careful client-side code plus dedicated test cases. It is the single most implementation-risky item in the list.

**Simpler option:** Format on blur only (`onBlur`) — user types raw digits, format fires when they leave the field. Much simpler (~15 lines), and covers the display case (V5) trivially. The UX is slightly worse (no live feedback) but standard and correct.

**Recommendation:** Ask the human whether "live" means as-you-type or on-blur. If the budget is tight, on-blur is the right call for a bug-fix stage.

### U3 — External Company conditional on role

The rule is: Admin + Company Member → can leave External Company empty; all other roles → require it. The app currently has no programmatic flag to distinguish "internal" from "external" roles. The session-level check elsewhere uses `externalCompanyId === null`, but for the **new-user form**, we need to know the rule at the role level before a user exists.

Options, in order of increasing complexity:
- **(a) Role name string match** — "if the selected role name is 'Admin' or 'Company Member', relax the requirement." Fragile if roles are renamed; the role data model allows arbitrary names.
- **(b) Permission code check** — internal roles have `MANAGE_USERS` or `MANAGE_FEATURES`; external roles don't. This requires the new-user page to either load all permissions per role (N+1 round-trips) or expose the role's admin-permission status in the roles list API.
- **(c) New boolean column on Role** — `isInternalRole boolean DEFAULT false`. Cleanest, but requires a schema migration. Migration is additive (nullable or defaulted) and low-risk.

**Recommendation:** Option (b) via a small API change — expose a boolean `requiresExternalCompany` in `GET /api/v1/orgs/[orgSlug]/roles` by checking whether the role has any admin-permission codes. No schema change needed. The human should confirm this is acceptable before the batch starts.

### U5 — Edit User page redesign (no mockup)

The human explicitly says "No mockup exists; design to fit the area, consistent with the Sage Ease theme." This is an open design task. Without at least a sketch or layout direction (e.g., "two-column info card alongside action panels", or "inline-editable fields with an edit button per section"), the developer is guessing. A poorly chosen redesign will require rework.

**Recommendation:** Block U5 until the human either provides a rough mockup or gives explicit permission for the developer to improvise. U4 (add the missing edit actions) can ship independently in the same batch without the redesign — the existing `max-w-lg` layout can gain an "Edit Profile" form section without a full redesign.

### D3 — Role-based KPI scoping (tenancy-adjacent)

This is labelled a design change above but it is worth flagging: the discriminator is `session.externalCompanyId === null` (internal) vs `!== null` (external). This is the same discriminator the list pages and API routes already use consistently — it's not inventing new logic, just applying an existing pattern to the stats query. The DAL change is straightforward.

## 5. Scope-Too-Big Check

**Verdict: One stage, but with an ordered execution plan and two blocker decisions resolved first.**

The 37 items break down as:
- ~20 are 1–20 line changes (true one-liners or small restructures)
- ~10 are medium (4–8 hours each): D3, L2, L3, U4, U3, Batch D form layout
- ~4 are risky/open-ended: C5 (live formatting), U5 (no mockup), U3 (design decision), L3 ("everywhere")
- ~3 are already done or trivial debt (PV1, X7, X4)

Total estimated agent effort across all batches: **30–45 hours** (≈ 4–6 agent sessions at the pace Stage 14 demonstrated). That is not too large for a solo developer with agent help over 1–2 days of human oversight.

**The stage should NOT split** on scope grounds. It should split only if:
- U5 cannot be decided before the stage starts (defer U5 to Stage 16)
- C5 live-formatting is chosen (that alone doubles Batch F's size and adds real risk)
